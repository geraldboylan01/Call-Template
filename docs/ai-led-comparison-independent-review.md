# Independent review of the AI-led comparison

10 September 2026. Source reviewed: `30eab9eb9c0737726c9a392ef1805f347aa3b10f`. This review made no production changes, changed no running experiment, and made no provider requests. Main evidence only: `diagnostics/ai-led-comparison-main-v1`; pilots are excluded.

## Interim scope and conclusion

The harness supports a paired comparison of the four **declared recovery strategies**, with the existing schemas, provenance normalizer, policy interface and verifier retained. It does not isolate “AI versus deterministic interpretation”, prove that a simpler production architecture is safe, or measure live approval/ASR/playback. Recovery policy, second-proposal prompt and scheduling rules change together by design. Do not describe the results as a pure prompt A/B or a historical release replay.

All 17 completed repetition-one case sets were independently checked: every arm received an identical initial request and raw response; no expected-result/rubric keys entered provider user envelopes; all 30 certificates had a consistent passing verdict, no findings, and a successful recorded authentication check. No inspected certified result used a wrong numerical input, reversed account owner, stale correction, or withdrawn unknown. This is a bounded observation, not evidence that such errors cannot occur. Several safety holdouts stopped after the common first response, so those successes do not distinguish recovery strategies.

## Harness findings

1. **Conditional pairing defect: unsuccessful HTTP/Responses payloads are not cached.** The protocol promises common-prefix reuse including errors. The wrapper at `scripts/compare-ai-led-recovery.mjs:137` caches only HTTP-successful payloads whose status is `completed`; its exception handler caches thrown errors. HTTP 4xx/5xx, `incomplete`, `failed`, and unparseable bodies therefore receive new samples in later arms. Such case-repetitions must be marked unpaired and rerun separately after a harness fix; do not silently include them as paired observations. No such violation occurred in the 17 r1 sets. House's thrown structural-repair AbortError was cached and replayed in the matching Option 2 prefix.

2. **Pairing otherwise has the right boundary.** Canonical JSON request hashes plus the accumulated request prefix prevent a response from a different rejected proposal being reused. The second `fresh` proposal bypasses the cache after the first verifier (`:118`), while its initial proposal and identical initial audit remain paired. Reverse order in repetition two reduces a consistent first-arm/provider-time advantage. Later audits can legitimately differ when production performs structural repair before verification and simple arms verify the original structurally defective proposal.

3. **No oracle leakage found.** `test.expected`, holdout rubrics and expected checks are used only after the provider call (`:156`, `:163`, `:188`). Outgoing `common` envelopes (`:51–63`) contain conversation, profile, policy and contracts. The `rethink` critique is another model's fallible output, explicitly identified as such; it is not ground truth. The `fresh` second **verifier** receives prior findings (`:95`), so “fresh” describes the second interpreter's evidence, not a verifier independently blinded to earlier criticism.

4. **Certificate decision is tied to the final simple-arm proposal.** A second ready candidate receives a second audit; certification requires readiness plus a consistent pass with no findings (`:68–71`, `:96–102`). A collecting second candidate cannot inherit an executable certificate from the first candidate. Actual certificate authentication and native-engine calls run afterward (`:165–174`). Calling the engine here proves computation under the certified input; it does not exercise live execution authorization or idempotency. The certificate's production prompt-version metadata is reused in this laboratory despite experimental second-proposal prompts; recorded arm/source artifacts, rather than that version string alone, establish experimental provenance.

5. **Time is a measured/simulated pipeline quantity.** Reused prefixes add the measured original latency through a `Date.now` offset (`:109`, `:125`), and new calls consume real time. This appropriately avoids crediting a cached arm with zero latency. Real abort timers do not themselves advance during replay; exact prefix pairing makes preceding budgets nearly equal, but near-boundary results should be examined rather than presented as precise live p95 latency. Current arms retain an adaptive repair-entry floor; simple arms use the hard deadline. That is a declared scheduling difference, not evidence that identical recovery work is faster under a different algorithm. Three cases run concurrently, so observed provider latency includes this experiment's concurrency.

6. **Corpus success and financial meaning are distinct.** The grader enforces exact titles for pension/child owners and selected labels for applicants. Holdout borrower confirmation checks merely search for “Ben”, which alone would not rule out “excluding Ben”. The independent reading below is necessary. Conversely, `valuesPass` is not a safety oracle: it deliberately ignores certification and does not fully grade read-back meaning, unknown handling, exclusions or citation semantics.

7. **A real simple-arm interface failure occurred.** R1 explicit-joint mortgage `rethink` call 3 returned `baseSnapshotRevision: 1` with `previousSnapshot: null`; the normalizer requires revision 0 and stopped before the second audit. The rejected proposal supplied in the critique itself has revision 1. Count this as an observed interface/protocol failure of this implementation of rethink, not a demonstrated wrong financial interpretation. The financial values in that unadopted raw proposal remained €240,000/4.1%/22 years/€500. No revision failure was bypassed for scoring.

## What the evidence establishes so far

Verifier rejection remains effective, but not every rejection is correct. Quote width, multi-turn corrections, aggregate derivations, unused metadata and pronoun paraphrases repeatedly turn correct financial understanding into internal bookkeeping tasks presented as client clarification. More repair opportunities can obtain a later approval without demonstrating an underlying change of financial meaning. Conversely, a fresh proposal can discard evidence even while preserving every financial value. These are reasons to evaluate the retained evidence/read-back interface as well as the recovery loop.

The five holdouts are valuable checks of the first interpretation, but mostly produce a correct common first response. A separate, clearly labelled bad-proposal recovery experiment should inject the same four structurally valid but semantically wrong first proposals into every arm: hypothetical rate as fact, superseded borrower selection, equal-value stale ownership, and forced readiness after a withdrawn rate. The independent verifier must reject those proposals; recovery can either return a supported correction or a safe non-executable result. These are adversarial probes, not new natural-sampling observations and must not be pooled into the main pass rate.

## Completion addendum — 11 September, primary-reviewer check

Both repetitions and the criticism-only follow-up completed. The primary reviewer checked all 170 arm outcomes for outgoing oracle fields and certificate consistency: no oracle fields were found; all 75 certified arm outcomes authenticated and had a consistent final pass. The paired first proposals also remained identical across all 34 main case-repetitions. These checks are recorded in `diagnostics/ai-led-comparison-main-v1/final-integrity-check.json`; they are not an exhaustive semantic oracle.

The primary reviewer then read the 23 distinct certified repetition-two confirmation texts across the main and follow-up studies. Selected borrowers, corrected values and equal-value account owners were retained in those texts. One material limitation was found: **fresh pension r2 omitted both retirement ages, 67 and 66**, despite including current ages, funds and contributions and despite the native inputs holding the right retirement ages. The existing corpus scored it as a pass; that does not establish informed confirmation of the retirement timing. It was already a greater-than-45-second outcome. This is a verifier false-negative concern under the intended read-back contract, not an executed wrong arithmetic input.

The final main counts are full repair 25/34, Option 2 31/34, rethink 27/34 and fresh 25/34. The separately run criticism-only arm scored 27/34. Scores below 45 seconds were 24, 28, 25, 24 and 27 respectively. All four original strategies corrected the numeric rate in the seeded hypothetical-rate probe; the different final outcomes arose from subsequent ownership review or timeout, not inability to change the rate.

The strongest additional state finding came from the seeded withdrawn-rate probe. The real reviewer rejected the old 4.1%, and each new AI proposal correctly returned collecting with rate unknown/absent. Full repair and Option 2 discarded that correct non-ready recovery and returned the old ready/4.1% provisional snapshot, while withholding certification. The simpler arms retained the collecting recovery. One rethink strict assertion expected literal null and failed on absence; absence was semantically unknown and remained non-executable. Preserve that distinction when revising tests.
