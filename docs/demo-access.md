# Demo requests and invitations

The homepage introduces Planéir's goal-led financial education service. The
demo flow saves information and confirmation only. It never calls AI, runs an
analysis, publishes results, creates a meeting or takes payment.

## Client journeys

- `/apply/`: public request form. Name, email, adult/education acknowledgements,
  and the current privacy/terms acknowledgements are required. Goals and figures
  may be left blank. The form keeps browser drafts before submission.
- `/demo/#access=…`: personal email link. The page removes the fragment, waits
  for an explicit Continue action, then exchanges the single-use, 24-hour token
  for a seven-day HttpOnly, Secure, SameSite=Strict cookie on the API host.
- `/demo/#invite=…`: reusable invitation. Accepting it grants enrolment, without
  disclosing any other participant's information. The first successful save
  creates an approved record and consumes one place. An authenticated pending
  applicant can instead upgrade their existing record.
- Pending applicants can save edits while waiting for approval. Approved people
  review their information and choose **Generate my analysis**. This saves the
  exact confirmed revision and explicitly states that generation is not connected.
- **Clear this device** clears the browser draft and session. **Delete my saved
  information** deletes the server record and its confirmations, links, sessions
  and queued email records. Unrelated historical services are not changed.

The public form and private form share `js/apply.js`; the private HTML is generated
from `apply/index.html`. Copy and public privacy/terms pages are generated by the
existing workspace page generator. Assistant guides remain prefill-only.

## Admin

Open `/app/demos.html` using the existing admin sign-in. It lists requests,
their current access/confirmation state and recent email delivery attempts.
The selected record shows the submitted information.

Actions: approve and email access, resend a private link, revoke demo access,
delete saved information, create a reusable invitation, and revoke an invitation.
New invitations default to seven days and 25 participants, configurable to
1–90 days and 1–10,000 participants. Copy a link when it is created: only its
hash is stored, so the full link cannot be recovered later. Create a replacement
if necessary. Revoking an invitation stops new enrolments; revoke an individual
record separately to remove an existing participant's generation permission.

Revoked participants may still read and delete their information through private
access. They cannot confirm it. Email changes are handled by support rather than
allowing an unverified replacement address to take over a saved record.

## Storage and API

Migration `0020_create_demo_flow.sql` adds independent tables to `LEADS_DB`:
requests, invitations, personal access tokens, sessions and a durable email
outbox. Contact details, goals, figures and confirmed snapshots are AES-GCM
encrypted with record-specific authenticated context. Lookup hashes and random
identifiers are not credentials. Raw access tokens are stored only within the
encrypted pending email payload and are removed after delivery/final failure.

`/api/demo/*` supports availability, session lookup/logout, request creation,
private read/edit/delete, invitation redemption, return-link recovery and
confirmation. `/api/advisor/demo/*` supports authenticated administration.
All changes require trusted Origin and JSON where a body is needed. Cookie
authenticated writes require CSRF. Admin endpoints explicitly reject disabled
admin authentication. Private responses use no-store and no-referrer.

Requests are never merged by typed email. Idempotency uses the browser's random
submission identifier. Edits require the current revision; confirmation requires
approval and the exact reviewed revision. Invitation triggers consume places
atomically in the same transaction as inserting/upgrading a request.

Confirmation returns `{status: "confirmed", generationAvailable: false}`.
The stored confirmed snapshot is the boundary for future generation work.
No consumer session, planner job or result is created by this implementation.

Receipts, access emails and admin notifications use the existing Resend sender.
Outbox writes are committed alongside record changes. Delivery retries use a
stable provider idempotency key, a lease and bounded retries within 23 hours.
The existing hourly scheduled handler retries due messages, removes expired
sessions/tokens and removes terminal delivery metadata after 30 days. Admin can
resend a fresh link after final failure. Emails contain no financial figures.

## Configuration and rollout

- `DEMO_REQUESTS_ENABLED`: defaults false in source. The production workflow
  reads the protected repository/environment variable of the same name.
- `DEMO_DATA_ENCRYPTION_KEY`: a separate Worker secret, base64url-encoded 32 random
  bytes. Never replace an existing key to activate the feature. Back it up in
  the operator's approved secret store. Optional key IDs default to `demo-v1`;
  previous keys use `DEMO_DATA_ENCRYPTION_PREVIOUS_KEYS_JSON` for reading and
  email recovery during rotation.
- Existing `RESEND_API_KEY`, `LEAD_EMAIL_FROM`, `LEAD_NOTIFICATION_TO`, and
  adviser authentication configuration are reused. Intake remains unavailable
  if the key, email sender or admin authentication is missing.

1. Run `npm run check:demo`, `npm run check:demo-browser`, workspace/browser,
   education-call, historical intake and build checks.
2. Run `node scripts/provision-demo-key.mjs` once to install a new key in the
   Worker and back it up in the protected GitHub production environment. It
   refuses to replace an existing key.
3. Apply additive migrations to `LEADS_DB` before deploying the Worker.
4. With the key provisioned, deploy using the existing production workflow
   so consumer bindings and protected runtime configuration are retained.
5. Verify private return access, storage/deletion and service email delivery
   before setting the protected `DEMO_REQUESTS_ENABLED` variable to true.
6. Publish the static pages only after `/api/demo/config` reports contract
   `demo-v1`. A disabled intake continues to show the form with a clear notice.

Rollback new enrolments by setting `DEMO_REQUESTS_ENABLED=false`. Existing
private access, edits and deletion continue to work. Keep the additive tables
and encryption key so existing requests remain readable. Generation remains
outside this release regardless of the intake setting.

Automated tests use fictional information and intercepted Resend requests;
they never deliver real emails or call an AI provider.
