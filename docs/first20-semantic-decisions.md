# First 20 semantic audit: decisions and contract read map

Updated 7 September 2026. This records the semantic workstream; the overall readiness report owns the final recommendation, browser evidence and release decision. No production deployment was performed by this workstream.

## What the preserved evidence showed

The archived baseline is `diagnostics/first20/paid-baseline/`, using the preserved source in `diagnostics/first20/baseline/source/` and planner/verifier versions v6/v3. Six of eleven synthetic cases passed. Its failures were not all incorrect financial interpretation:

- **P0 integrity / P1 completion: acknowledged unknowns could disappear from the blocked list when the model obeyed its instruction not to repeat them in `missing`.** The baseline `mortgage-acknowledged-unknown-must-wait.json` contains a collecting module with both `missing: []` and `blocked: []`. Readiness must derive this restriction from the recorded client action, not from what the model lists.
- **P1: a later confident answer had no supported route to clear the earlier acknowledgement.** The baseline recovery case supplies a definite rate in a later turn. The current implementation represents that resolution explicitly and requires chronology, evidence and independent certification before the shared session removes it.
- **P1: bookkeeping mistakes were reaching the consumer as unanswered financial questions.** The house-purchase baseline had the intended applicant and cash figures, but quotations contained inserted ellipses and referenced the wrong turn. Structural provenance correctly dropped those citations. The planner then received no opportunity to repair its own citations before the conversation asked again.
- **P1: the pension playbook's Dev Panel compatibility fields conflicted with the concise native consumer contract.** The baseline correctly preserved both people's pension facts, including Ben's corrected pot, but authored additional root salary/pot/contribution aggregates without supporting evidence. Those were then reported as missing. The native validator requires the owner records; the pension normalizer derives root aggregates itself.
- **P1/P2: extractor and verifier disagreed about spoken materiality and repairable errors.** The verifier sometimes asked for optional/default bookkeeping already deliberately omitted by the extractor, or treated an already-resolved correction as a fresh client ambiguity. A correct input could therefore fail to reach its confirmation.

The v7/v4 run in `diagnostics/first20/paid-final/` is also preserved. Seven of twelve cases passed. Two failures were provider/network failures; three completed model journeys still failed on mortgage/pension read-back completeness or house-purchase citations. In particular, the repair fixed one finding but dropped other material that the first proposal already contained. The exact failed proposal was absent from its repair request. These results are evidence of remaining failure, not a release pass.

## Decisions and why they generalise

1. **Keep semantic interpretation in the AI and mathematics in the existing engines.** No financial-language regex, phrase compiler, engine formula or financial assumption was added. Code checks JSON identity, provenance, chronology, policy, versions and signatures. Exact-substring quotation checks establish where evidence came from; the verifier still decides what it means.

2. **Derive unknown restrictions from the server-owned acknowledgement list.** A relevant module stays unavailable for an uncovered requirement even when its model-authored `missing` list is empty. A supplied approved default can cover a requirement without making it a client fact. Questions solely about acknowledged paths leave both the missing and ambiguity ask lists.

3. **Represent recovery as an AI proposal with an independently certified outcome.** Each proposed resolution carries the requirement path, later client turn and exact quote. Code requires an existing acknowledgement, a strictly later user turn, an actual non-null input and surviving evidence for that requirement from that turn. Same-turn answers, adviser turns, missing chronology and legacy acknowledgements without a source cannot clear it. The verifier sees both the original acknowledgement and proposed resolution. The certificate binds the resolution hash, and the shared Durable Object removes only the matching module/path/source acknowledgement after authenticating that certificate.

4. **Repair mechanically unsupported ready inputs once before asking the consumer again.** Only a would-be complete plan with structural support issues and no genuine outstanding questions receives this repair. The same transcript, policy and independent verifier remain authoritative. Structural repair and semantic-verifier repair share one total repair budget; there is no retry loop. A failed repair stays unconfirmable. Completed repair calls, discarded verification calls and cached tokens are all counted exactly once.

5. **Make the native pension contract explicit in the extractor.** `pensions[]` carries each owner's figures. Legacy root age/salary/pot/contribution fields from the Dev Panel example need not be authored in this consumer input. Removing that prompt conflict avoids asking a person to provide a synthetic household contribution percentage. Engine-generated aggregates remain engine-owned and are not reintroduced as conversation facts.

6. **Align the verifier with the same confirmation rules used by the extractor.** Later explicit corrections replace earlier figures; differing old values alone are not fresh ambiguities. Incorrect quotes, omitted supported facts and inaccurate attribution are repairable planner findings. Genuinely competing client meanings still require a client answer. Routine calculation-date metadata, an unspecified optional fixed payment and an invariant repayment discriminator do not require an extra spoken question. Client-supplied payments/dates and material financial assumptions remain material.

7. **Give repairs the actual failed proposal and require minimal corrections.** Both repair paths now send `priorAuditFindings.failedProposal`. It includes the exact current read-back and surviving supported content rather than only an older conversation snapshot. Repairs preserve unaffected owners, values, assumptions, valid quotations and material read-back content while correcting the identified defect. The original proposal is explicitly not evidence. The 60–90-word preference is not a cap: material figures, ownership, precision, exclusions and financial assumptions take precedence. The independent verifier must still pass the resulting exact prompt.

8. **Version the changed prompt contract.** Current defaults, deployment configuration and probe/test metadata use planner v8 and verifier v5. Earlier diagnostic archives retain the actual versions they ran. The v8/v5 paid rerun is reported separately by the overall audit; the earlier v7/v4 failures must not be relabelled as results of this repair-context change.

## Expectation audit and remaining limits

An exact display title such as `Aoife` is not required by the native pension contract; the existing profile adapter itself produces `Aoife pension`. Owner identity and the owner's figures must be checked together without requiring one arbitrary display spelling. Conversely, Anna and Anne must remain distinct; matching similar names loosely would weaken the test.

The original mortgage phrase “jointly held by me, Aoife, and Ben” was flagged by a baseline verifier as a possible third borrower. It can also be a natural appositive given the primary profile identity. The original evidence remains intact, and a separately named explicit-two-owner case removes that wording uncertainty for comparison. This does not justify tolerating wrong owners or discarding the original failure.

Strict schema and free mocked-provider checks do not prove the real model consistently understands consumers. The latest complete paid evidence still includes authentic read-back/citation failures. One run per case is not a reliability estimate; larger repeated and incremental-turn corpora remain necessary before claiming broad consumer readiness.

Unknown recovery intentionally fails closed when its original source turn is unavailable. Current direct planning requests source references, retains 24 recent client turns and up to 80 referenced turns, and reconciliation loads at most 200 final turns. Very long sessions can exhaust that history and leave an old unknown unrecoverable. This is a completion risk, not permission to invent chronology.

This workstream did not independently validate current Irish law, market rates, microphone capture, mobile browsers or production networking. Dated financial policy verification and Speak/Type transport evidence belong to the overall readiness audit. No claim of all-seven live consumer success should be inferred from the native-engine fixture matrix alone.

## Final audit update

The final prompt metadata is v9/v6. Two further protocol clarifications require the actual numeric values of material financial assumptions and explain that `sourceTurnId` is the original uncertainty turn while `turnId` is the later resolving answer. No financial defaults changed. The v9 paid run passed 9/12; PBS, college and house purchase still failed. This supersedes references above to v7/v4 or v8/v5 as the latest run. [The readiness report](first20-readiness.md) preserves all run totals, comparisons and the NOT READY recommendation.

The existing internal-repair test's exact old instruction phrase was updated to the current wording and strengthened to compare the full failed proposal against the verifier's actual proposal. Its financial, certification and call-budget assertions were retained.
